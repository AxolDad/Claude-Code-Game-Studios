# /setup-engine — Section 7.5: Scaffold the Engine Project

> Part of `/setup-engine`. `SKILL.md` names when to read this file; the settings it
> resolved and the rules under its later headings still apply here.

## 7.5 Scaffold the Engine Project

**Without this step the framework produces source files no engine can open.**
`/dev-story` writes `.gd`/`.cs`/`.cpp`/`.rs` under the resolved code root, and the `minimal` path
advertises "four steps to running code" — but no other skill writes a
`project.godot`, a Unity project, a `.uproject` or a `Cargo.toml` for the engine to load.

### Godot — write `project.godot` if one is absent

**Never overwrite an existing `project.godot`.** If the file is already there,
say so and skip to Section 8 — the developer has a project and its settings are
theirs.

Show the proposed file, then ask: *"May I create `project.godot` at the repo
root?"* On approval, write:

```ini
config_version=5

[application]

config/name="<project name>"
config/features=PackedStringArray("<major.minor>", "<renderer feature>")

[rendering]

renderer/rendering_method="<rendering method>"
```

Fill it from decisions already made — do not ask again:

| Field | Source |
|-------|--------|
| `config/name` | the brief's working title, else the repo directory name |
| `<major.minor>` | `engine.version` from Section 3, major and minor only (`4.7.2` → `4.7`) |
| `<renderer feature>` / `<rendering method>` | the `rendering` value chosen in Section 5.5.1 — Compatibility → `"GL Compatibility"` / `gl_compatibility`; Forward+ → `"Forward Plus"` / `forward_plus`; Mobile → `"Mobile"` / `mobile` |

**Leave `run/main_scene` unset.** There is no scene yet at engine-setup time.
Add a comment saying `/dev-story` or the developer sets it once a scene exists;
an empty project with no main scene opens fine in the editor.

**Then verify, and report what the verification actually was.** If the engine
binary was found in Section 3, run its headless import
(`godot --headless --path . --import`) and report the result — read the output
for `ERROR`, because the import exits 0 even when something in the project
fails to load. On Godot 4.7, this first import of a new project sometimes exits
139 (a crash on exit) after it has finished; run it once more and report the
second result. If the binary was
not found, or its version differs from the pinned one, write
**`project.godot NOT VERIFIED — <reason>`**. The `config_version` and feature
strings are stable across Godot 4.x, but "stable in the versions I know" is not
the same as "checked against the version you pinned", and only the run
establishes the latter.

### Bevy — write the crate's missing files

Unlike a Unity project, a Cargo crate is plain text and its contents are known:
**B4** in `references/bevy-config.md` holds the exact files. Bevy needs both
`src/lib.rs` and `src/main.rs`: game code goes in the library so `tests/` can
import it.

**Never overwrite an existing file — check each of the four separately.** Glob
`Cargo.toml`, `src/lib.rs`, `src/main.rs` and `assets/`. What exists is the
developer's; what is absent gets written. `.claude/scripts/write-guard.sh` only warns
on a `Write` over an existing `Cargo.toml`, and not on an `Edit`, so do not rely on it,
and do not `Edit` one here either. When some files already exist:

- **`Cargo.toml` exists:** take `<crate>` from its `[lib] name`, else its
  `[package] name` with hyphens as underscores. If it has no `bevy` dependency, or
  one that disagrees with the pinned version's major and minor, say so with both
  values and tell the developer the line to change. Do not change it.
- **`src/lib.rs` exists and does not define `GamePlugin`:** the B4 `src/main.rs` would
  not compile against it, so do not write that file. Show the developer the lines
  it would need.
- **`src/main.rs` exists and `src/lib.rs` does not:** write `src/lib.rs` and say the
  existing `main` must add `GamePlugin` itself, and that game code in `main.rs` cannot
  be imported by `tests/` until it moves into the library.

Show the files you will write, then ask: *"May I create [the absent files]?"* On
approval, write them exactly as B4 gives them. The window this opens shows only
Bevy's clear colour: nothing is drawn until the game spawns a camera. Say so, so an
empty window does not read as a failure.

**Then verify, and report what the verification actually was.** Run `timeout 1800 cargo
check`. Its first run compiles all of Bevy, which can pass the Bash tool's 10-minute
limit, so run it in the background and wait for it. It also creates `Cargo.lock`,
which Section 8 reads.

- Exit 0 → `Cargo.toml verified: cargo check exit 0`.
- Non-zero with `error` lines → report them and resolve them before finishing. On
  Linux, missing system packages fail here; the list is
  `g++ pkg-config libx11-dev libasound2-dev libudev-dev libxkbcommon-x11-0 libwayland-dev libxkbcommon-dev`.
- Exit 124, no `cargo`, or a `rustc` below the minimum from Section 3 →
  **`Cargo.toml NOT VERIFIED — <reason>`**. The files look right, but nothing
  has compiled them against the pinned version.

### Unity and Unreal — instruct, do not fabricate

A Unity project and an `.uproject` are editor-generated and span many files,
several of them binary or machine-specific. This repo cannot source their
correct contents, and a hand-written scaffold would be the exact failure
Section 7's sourcing rule forbids — something that looks finished and is quietly
wrong.

Tell the user, in one short block, that CCGS does not create the project for
these engines and they should create it first:

- **Unity** — create the project in Unity Hub at the repo root, choosing the
  template matching the 2D/3D answer from Section 2, then re-run `/setup-engine`.
- **Unreal** — create the project in the Epic launcher or via `UnrealEditor`,
  then re-run.

Report the outcome in the Section 12 summary either way — created, already
present, or "not created, engine requires the editor" — so the user leaves this
skill knowing whether a runnable project exists.

> **Deliberately not a `project.yaml` key.** An `engine.project_scaffolded` flag
> would be written here and read by nothing, which is a dead setting — the same
> writer-without-reader defect the config gates exist to catch. The filesystem is
> the source of truth: any skill that needs to know globs for `project.godot`,
> `*.uproject`, `ProjectSettings/ProjectVersion.txt`, or `Cargo.toml`.
